◆ Payment lifecycle

One payment, five auditable states

What happens on every capture

The money path is deliberately small: authenticate, lock, transition, write the settlement and audit entry, commit, then notify outside the transaction.

The idempotency key has a unique index on (merchant_id, idempotency_key). Concurrent replays race on that index, and the loser returns the winner's payment with idempotent-replayed: true.

◆ Capabilities

What makes it production-grade

🛡

Dual authentication

JWT for dashboard users, API keys for server-to-server integrations — bcrypt-hashed, Helmet-protected, rate-limited.

🔁

Idempotent by design

idempotency_key dedupe with a race-condition handler on Postgres unique violations — no double charges.

🔒

Concurrency-safe ledger

Captures and refunds take a FOR UPDATE row lock before reading state, so simultaneous requests settle once and cannot over-refund.

💰

Settlement engine

2% platform fee, 18% GST and merchant net computed in pure, unit-tested math with drift-free rounding.

🔔

Signed webhooks

Real HTTP delivery signed with HMAC-SHA256. Status tracked, failures retryable via POST /api/webhooks/retry/:id.

🧾

Audit trail API

Every state change records old and new values. Read the full timeline at GET /api/payments/:id/audit.
